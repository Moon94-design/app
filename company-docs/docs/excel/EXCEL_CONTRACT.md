# 엑셀 업로드 정책 계약서 (EXCEL_CONTRACT)



**작성일**: 2026-02-06  
**목적**: Phase5-1 코딩 전에 "업로드 정책 + 충돌 정책 + 버전 정책"을 확정하여 재작업 최소화

---

## TL;DR (반드시 읽기)
DRAFT / 임시 / 변경 가능

“고정 정책”으로 쓴 부분을 권장(default) + 변경 가능

현장 엑셀 서식 기준으로 조정한다
1. **목적**: 엑셀 1차 방어(파싱/검증) + 웹앱 2차 방어(UI 확인) 이중 구조
2. **업로드 정책**: **Policy A (권장)** — FAIL 1건이라도 있으면 전체 저장 거부
3. **충돌 정책**: **Error (권장)** — 중복키 충돌 시 사용자 확인 필요 (저장 거부)
4. **템플릿 버전**: TEMPLATE_VERSION 필드 필수, 버전 불일치 시 경고/거부
5. **감사 로그**: 업로드 사용자/시각/파일명/버전/행수/OK/FAIL 카운트 기록
6. **Phase5-1 범위**: 파싱/검증/미리보기만 구현 (저장 반영은 Phase5-2 이후)

---

## 1. 업로드 정책 (저장 방침)

### Policy A: All-or-Nothing (권장) ✅
- **규칙**: FAIL 행이 1건이라도 있으면 전체 저장 거부
- **장점**: 데이터 일관성 보장, 부분 저장으로 인한 혼란 방지
- **단점**: 1건 실패 시 전체 재업로드 필요
- **적용**: Phase5-1에서 기본 정책으로 채택

### Policy B: Partial Save (보류)
- **규칙**: FAIL 행 제외, OK 행만 저장
- **장점**: 일부 실패해도 성공 데이터 활용 가능
- **단점**: 부분 저장으로 데이터 불완전, 운영 혼란 가능
- **적용**: Phase5-2 이후 선택 옵션으로 검토

---

## 2. 충돌 정책 (중복키 충돌 시)

### Error: 충돌 시 저장 거부 (권장) ✅
- **규칙**: 중복키 충돌 발생 시 전체 저장 거부, 사용자 확인 요청
- **적용 상황**:
  - 엑셀 내부 중복 (같은 파일 내 동일 키 2개 이상)
  - DB 충돌 (DB에 이미 존재하는 키)
- **장점**: 사용자가 의도 확인 가능, 실수 방지
- **단점**: 충돌 시 사용자 개입 필요
- **적용**: Phase5-1 기본 정책

### 기타 정책 (보류)
- **Upsert**: 충돌 시 덮어쓰기 (위험, 추후 검토)
- **Skip**: 충돌 행 건너뛰기 (부분 저장과 동일 문제)
- **Version**: 버전 추적 (복잡도 높음, Phase6 이후)

---

## 3. 템플릿 버전 정책

### 버전 필드 필수
- **필드명**: `TEMPLATE_VERSION` (엑셀 메타데이터 또는 첫 행)
- **형식**: `v1.0`, `v1.1` 등 (시맨틱 버전)
- **위치**: 첫 시트 첫 행 또는 별도 메타 시트

### 버전 불일치 처리
- **권장**: 버전이 1개 이상 차이 나면 **경고 + 저장 거부**
- **이유**: 컬럼 구조 변경 시 파싱 오류 방지
- **예시**:
  - 현재 지원 버전: v1.0
  - 업로드 파일 버전: v0.9 → **거부 (너무 오래됨)**
  - 업로드 파일 버전: v2.0 → **거부 (미지원 버전)**

---

## 4. 감사 로그 정책

### 최소 기록 항목
- **사용자**: 업로드 실행자 이름/ID
- **시각**: 업로드 시각 (ISO 8601)
- **파일명**: 원본 파일명
- **템플릿 버전**: TEMPLATE_VERSION 값
- **행 수**: 총 행수 / OK 행수 / FAIL 행수
- **결과**: SUCCESS / PARTIAL / FAIL

### 선택 항목 (보류)
- **파일 해시**: SHA-256 (추후 검토, Phase5-2 이후)
- **상세 에러 로그**: 각 행의 에러 메시지 (별도 테이블)

---

## 5. Phase5-1 범위 (할 것 / 하지 않을 것)

### ✅ Phase5-1에서 할 것
1. **파싱**: 엑셀 파일 → JSON 파싱 (SheetJS)
2. **검증**: 필수값/타입/허용값/중복키 검증
3. **미리보기**: 검증 결과 UI 표시 (OK/FAIL/WARN)

### ❌ Phase5-1에서 하지 않을 것 (보류)
1. **저장 반영**: DB merge 로직 (Phase5-2 이후)
2. **서버 제공통제**: 권한별 업로드 허용 (Phase6 이후)
3. **RBAC**: 역할별 접근 제어 (Phase6 이후)
4. **보고서**: 업로드 이력 조회/통계 (Phase6 이후)

## A. 운영 예시 (실패 처리 흐름)

### Case 1: 엑셀 내부 중복
```
파일: production_lines_20260206.xlsx
행 3: shift=주간, product=분쇄품, item=PP → OK
행 5: shift=주간, product=분쇄품, item=PP → FAIL (행 3과 중복)

결과: 전체 저장 거부 (Policy A)
메시지: "엑셀 내부 중복키 발견 (행 3, 5). 파일 수정 후 재업로드"
```

### Case 2: DB 충돌
```
파일: production_lines_20260206.xlsx
행 3: recordDate=2026-02-06, shift=주간, product=분쇄품, item=PP
DB: 이미 동일 키 존재

결과: 전체 저장 거부 (Error 정책)
메시지: "DB에 이미 존재하는 키 (recordDate=2026-02-06, shift=주간...). 수정 또는 삭제 후 재업로드"
```

### Case 3: 필수값 누락
```
파일: production_lines_20260206.xlsx
행 7: shift=주간, product=분쇄품, item=(빈값), bags=100

결과: 전체 저장 거부 (Policy A)
메시지: "필수값 누락 (행 7, 컬럼: item). 파일 수정 후 재업로드"
```

## C. 정책 선택 근거

### 왜 Policy A (All-or-Nothing)?
- **일관성 우선**: 생산 데이터는 정확성이 중요, 부분 저장 시 혼란 가능
- **사용자 확인**: 실패 원인을 명확히 파악 후 재업로드 (실수 방지)
- **운영 단순화**: "전체 성공" 또는 "전체 실패"로 이분법적 처리

### 왜 Error (충돌 시 거부)?
- **실수 방지**: 중복 저장 시 데이터 손실 위험 (덮어쓰기 금지)
- **사용자 의도 확인**: 충돌 시 사용자가 직접 판단 (수정/삭제/무시)
- **안전 우선**: 초기 정책은 보수적으로 시작, 추후 Upsert 옵션 추가 가능
