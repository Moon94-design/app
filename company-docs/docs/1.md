# CONTRACT_SSOT.md — company-docs 정본(SSOT) 계약서 (수정본)

## TL;DR (필독 5줄)
1) **기능 변경 0**을 최우선으로, 작은 단위로 수정하고 항상 `npm run build` 게이트를 통과한다.  
2) **페이지에 로직 추가 금지**: 제목/태그/연계 로직은 정본(SSOT) 훅·블록·엔진에서만 구현한다.  
3) **연계 강제**: 선택 UI에는 항상 추가(등록)/수정(rename·중복방지)이 포함되며 페이지 이동 없이 그 자리에서 해결한다.  
4) **TS strict 준수**: `import type`/unused 금지(TS1484/TS6133/TS6196).  
5) **결과 문서 규약**: 250줄 OR 2,000자(내외), 예외 시 첫 줄에 `EXCEPTION USED: 사유` 명시(섹션별 제한 준수).

## 0) 목적(정체성)
이 프로젝트의 최종 목표는 **“회사 운영 데이터 플랫폼”**이다.
- 회사의 기준정보 + 일일기록 + 이슈/조치 + 조회/보고서까지 한 곳에 모아
- **효율적으로 파악/검색/정리/분석**할 수 있게 한다.
- 이슈/조치는 중요한 축이지만 “정체성의 전부”는 아니며,
  전체 파악(조회/보고서)과 연계 구조가 최종 가치의 핵심이다.

## 1) 하드 고정 원칙(절대 위반 금지)
1. **후반(서버/보안/운영) 이식 우선**
   - 지금 당장 편한 구현보다, 서버/권한/감사로그/운영까지 확장 가능한 구조가 최우선이다.

2. **정본(SSOT) 우선**
   - 동일 로직이 2번 보이면 정본으로 올린다.
   - 페이지마다 “살짝 다른 구현” 금지. 차이는 옵션(파라미터)로만 표현한다.

3. **연계 강제(페이지 이동 최소화)**
   - “선택(기존 불러오기)” UI에는 항상 **추가(등록)/수정(rename/중복방지)** 기능이 포함돼야 한다.
   - 등록 페이지로 갔다가 돌아오는 UX는 기본 금지(연계 엔진으로 그 자리에서 해결).

4. **스키마 정본 → 페이지 조립**
   - schema가 default/normalize/validate/toRecord를 책임진다.
   - 페이지는 스키마를 호출만 하고, 검증/정규화 로직을 복제하지 않는다.

5. **TS strict 준수**
   - unused import/unused function은 빌드 실패(TS6133/TS6196).
   - verbatimModuleSyntax 때문에 type은 import type 필수(TS1484).

## 2) 패치/앵커/롤백 운영(현실 버전)
### 2.1 patch/rollback은 유지(필수)
- 코파일럿이 즉시 고치더라도, “방향/규약 위반”을 되돌릴 안전장치가 필요하다.
- 기본은 git이지만, 작업 중 실험/되돌림은 patch/백업이 빠르다.

### 2.2 앵커는 “정본(SSOT) 파일 위주”로만 강하게 운영
- 모든 파일에 앵커를 강제하지 않는다.
- **정본 파일(재사용되는 훅/블록/연계 엔진/태그 엔진)**에만 앵커를 적극적으로 둔다.
- 페이지 파일은 코파일럿이 수정하되, “페이지 로직 금지” 규칙으로 통제한다.

## 3) 데이터 계약(IDs / Refs / Facets)
### 3.1 모든 문서/하위항목은 ID 필수
- Document.id 필수
- Line/Item/Action 등 하위 항목도 id 필수
- recordDate(기록날짜) 필수, createdAt/updatedAt 저장

### 3.2 Ref(연계)의 단일 형식
연계는 무조건 Ref로 저장한다:

Ref = { type, id, label, meta? }

- type: "partner" | "vehicle" | "agency" | "equipment" | "daily:production" | ...
- id: string
- label: string (화면 표시용)
- meta?: object (선택: 필터/표시 보조)

### 3.3 조회/보고서를 위한 facet 필드(태그는 보조)
태그는 보조이고, 필터 주력은 facet이다.
예:
- issue: type/channel/status/severity/tags/refs
- action: status/dueDate/tags/refs
- productionLine: site/shift/product/item/bags/kg
- logisticsLine: direction/item/kg/unitPrice/partnerRef/vehicleRef  
(각 도메인 스키마에 최소 facet 유지)

## 4) 정본 기능(SSOT) 목록
### 4.1 공통 폼 블록(페이지는 조립만)
- RecordHeaderBlock: 기록날짜/지부/작성자/직책
- AutoTitleBlock: 제목 자동완성(제목칸 클릭 시 auto on, 수동 수정 시 auto off)
- TagBlock: 태그 입력 + 추천 + 색상 + dismiss + 더보기 + 개인태그 삭제
- MainContentBlock: 내용 입력  
(이 4개는 모든 페이지에서 재사용)

### 4.2 연계 엔진(어디서든 재사용)
- LinkPicker(모달/패널): 검색+선택+추가+수정(rename/중복방지) 통합
- adapters: partner/agency/vehicle/equipment/employee/...  
  - 데이터 소스 + rename 규칙 + create form만 담당
- 페이지는 openLinkPicker(...) 호출만 한다

### 4.3 태그 엔진(정본)
- 기준(시스템) 태그: 파란색(진한 톤)
- 개인 태그: 연회색 + 본인이 삭제 가능
- 내용 기반 추천: “전체 내용 포함 + suffix 보조” + 최대 5개(더보기로 확장) + dismiss 가능
- 수동 입력 추천 드롭다운도 system/personal 색상 구분
- 개인 태그는 타 사용자에게 비공개(정책), 서버에는 통계용으로 저장 가능

## 5) 이슈/조치 설계(단일 통합 모델)
### 5.1 이슈는 “통합 단일 모델”
- 이슈는 하나의 모델이며, 분야별로 이슈가 분기되지 않는다.
- 이슈 분류는 **선택값 + 태그**로 처리한다.

#### 이슈 분류(초기 고정 최소 세트)
- 클레임 / 민원 / 안전 / 품질 / 설비 / 기타

> “갈등/오류” 등은 초기엔 확정하지 않는다.  
> 필요성이 확인되면 추후 승격(기타 + 태그로 먼저 운영).

### 5.2 이슈는 refs로 모든 기록/기준정보를 참조
- 생산/유통/사무/재고/영업 등 어떤 기록이든 refs로 연결 가능
- 기준정보(거래처/차량/설비/기관/업체/담당자 등)도 refs로 연결 가능

### 5.3 조치는 이슈에 종속되며 “조치기록” 페이지에서 관리
- 진행중 이슈 선택 → 조치 작성 가능
- 완료 처리 흐름:
  - 이슈에서 완료 처리 시 조치기록으로 전환(또는 조치 작성 유도)
- 조치도 refs/tags 가능
- 생산 등 다른 기록 페이지에서 이슈/조치를 직접 “생성”하는 것은 기본 금지
  - 필요 시 ref 연결만 허용(복잡도 방지)

  ## 6) 조회/보고서 및 권한(서버 단계 전제)
### 6.1 권한/보안(RBAC)
- 일반 계정:
  - 조회는 “요약/부분”만
  - 전체 파악/통합 분석 조회는 불가
  - 내보내기/인쇄 제한
- 관리자 계정:
  - 모든 조회/보고서/통계/내보내기 가능

**중요:** “가리기”가 아니라 **서버에서 허용된 데이터만 제공(제공 통제)** 한다.

### 6.2 조회(통합검색) 기본 구조
- 통합검색 + 필터 + 표시 템플릿(복수 선택)
- 필터 예: 기간, 지부, 작성자, 거래처, 품목, 입고/출고, 일지 종류, 태그, 이슈 등

### 6.3 보고서(초기 정의)
- 기록 없는 날 포함/미포함 옵션
- 극단값 포함
- 단가 평균은 총액/총kg 평균 단가
- 기간별 변동폭(1일/1주/1개월/3개월/6개월/1년)

### 6.4 해결방안 메뉴(확장 목표)
- 이슈의 tags/refs/action 히스토리를 기반으로
  - 관련 기관/업체/연락처/과거 조치 목록을 제공
- 이 기능은 일반 계정에도 제공 가능
- 숨길 대상은 “회사 전체 파악/통합 분석 조회(관리자 전용)”이다

## 7) 코파일럿 작업 지시 규칙(매 작업 공통)
- 작업 시작 전 이 문서를 읽고 준수할 것
- “페이지에 로직 추가” 금지:
  - 제목 자동/태그 추천/색상/연계추가 로직은 정본 훅/블록/엔진에서만
- 동일 기능이 2번 보이면 정본으로 승격할 것
- 변경은 작게(1~2파일) + 빌드 통과 확인
- 새 파일/새 훅/새 유틸을 만들기 전:
  - 기존 정본(SSOT)에 이미 비슷한 기능이 있는지 먼저 확인할 것
- 변경 후 반드시 확인:
  - `npm run build` 성공
  - Production/Issue/Action에서 제목/태그/연계 UX가 동일하게 동작

## 9) (선택) 정본 폴더(SSOT) 도입 지침
정본 파일을 한곳에 모아 “무엇이 쓰이고/안 쓰이는지”를 명확히 한다.

권장 구조:
- `src/ssot/`
  - `schema/` (정본 스키마: default/normalize/validate/toRecord)
  - `linking/` (Ref/LinkPicker/adapters)
  - `tags/` (tag index/추천/정책)
  - `forms/blocks/` (Header/Title/Tag/Content 블록)
  - `index.ts` (정본 재export)

도입 순서(안전):
1) 파일을 바로 이동하지 말고 `src/ssot/index.ts`로 먼저 re-export(수입 경로 통제)
2) import가 ssot를 통해서만 들어오게 된 뒤 실제 파일 이동

**SSOT import 규칙**: 정본 기능은 반드시 `src/ssot/index.ts`로만 import할 것
