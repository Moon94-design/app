작업 트랙
1) API 계약 확정
- API 스타일은 REST로 고정한다(Phase 6 기준).
- REST 계약을 문서로 고정(경로, 메서드, 페이로드, 에러코드).
- 도메인별 최소 엔드포인트 정의: partner, daily, issue/action, browse 집계.
- 버전 전략(v1 prefix 또는 스키마 버저닝) 확정.
- DTO-스키마 정합성 규칙 고정:
  - API DTO는 `kernel/schema`에서 파생하거나, DTO를 별도 정의할 경우 `kernel`에 단일 매핑 SSOT를 둔다.
  - 프론트 타입/DTO/DB 스키마가 독립적으로 분기되지 않도록 1:1 매핑 표를 유지한다.

2) 인증/인가 모델 확정
- 인증 방식 선택(세션/토큰) 및 만료/갱신 정책 정의.
- 권한 모델 정의(예: admin/editor/viewer) + 엔드포인트별 접근 정책 표 작성.
- 감사 로그 최소 항목(사용자, 액션, 대상, 시각) 정의.

3) DB/마이그레이션 설계
- DB 선택(PostgreSQL 등) 및 엔티티-테이블 매핑 확정.
- 초기 마이그레이션 스크립트 작성 전략(DDL + seed 최소셋) 결정.
- 로컬 스토리지 데이터를 서버로 이전하는 매핑/정합 규칙 정의.

4) 업로드/엑셀 처리 위치 확정
- 파일 처리 책임 위치 확정(서버 우선 권장).
- 업로드 검증(확장자/크기/스키마) 정책 정의.
- 실패 재처리/중복 업로드 방지 규칙 정의.
- idempotency 정책 확정:
  - 동일 파일/동일 배치 재업로드 시 중복 반영 방지 키를 사용한다.
- 부분 실패 전략 확정:
  - 전체 실패/부분 반영 중 하나를 명시하고, 사용자 피드백 포맷(오류 행/사유)을 고정한다.

5) 프론트 연동 전환 계획
- domain repo의 impl 교체 전략 수립(local -> server).
- 기능 플래그 또는 환경변수로 점진 전환(읽기 우선 -> 쓰기 전환).
- Partner 도메인 기준 단계 고정:
  - 1단계: 서버 읽기(`getAll`/`getById`)만 전환.
  - 2단계: 서버 쓰기(`upsert`/`upsertMany`/`remove`) 전환.
  - 3단계: local fallback 제거.
- 장애 대비 롤백 경로(서버 장애 시 임시 fallback) 정의.

완료 정의(Phase 6 DoD)
- API/DB/인증 정책이 문서로 고정되어 팀 내 동일 해석 가능.
- 최소 1개 도메인(partner)에서 서버 읽기/쓰기 E2E 검증 완료.
- 프론트는 domain repo를 통해 서버 impl로 전환 가능하며, 하드코딩 키/직접 storage 접근 0.
- 실패 시 롤백 절차가 문서화되어 재현 가능.
- 읽기 우선 전환 검증 완료:
  - Partner는 반드시 읽기 전환 완료 후 쓰기 전환으로 넘어간다.
  - 쓰기 전환 전에는 local fallback 제거 금지.
- DTO-스키마 정합성 검증 완료:
  - Partner 타입/DTO/DB 간 매핑 문서가 최신 상태이며 불일치 0.
- 업로드 정책 검증 완료:
  - idempotency 키 정책과 부분 실패 처리 정책이 문서/구현 모두에 반영됨.
